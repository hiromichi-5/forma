# 招待作成時のメール送信失敗ハンドリング

## 背景・課題 (Background/Problem)

- `CreateInvite` は招待レコードを DB に作成した後、招待メールを送信する
- メール送信が失敗した場合、招待レコードが DB に残ったままになる
- 孤立した招待が存在すると、同一メール・同一フォームへの再招待が `ACTIVE_INVITE_ALREADY_EXISTS` で拒否される
- ユーザーはメールを受け取っていないため accept URL を知らず、管理者が手動で招待を削除するしかない

## 決定事項 (Decision)

メール送信が失敗した場合、作成済みの招待レコードを明示的に削除する。

### 理由 (Reasons)

- トランザクション内に外部 I/O（メール送信）を含めない設計原則を維持できる
- DBコネクションの保持時間に影響を与えない

### 受け入れるトレードオフ (Accepted Trade-offs)

- Deleteが失敗する可能性がある。メール送信失敗と DB 削除失敗が同時に起きた場合、孤立した招待が残る。
- ただし、同時に発生する可能性は低いことが期待され、管理者が手動で削除することで回復可能なため、許容する。

## 検討した別の選択肢 (Alternatives Considered)

### 案1: トランザクション内で招待作成 + メール送信

- メリット: 招待とメール送信の整合性が保証される。孤立した招待が残らない。実装がシンプルで既存の UnitOfWork パターンに沿えば良い。
- デメリット: SES の API レイテンシの間 DB コネクションを保持する。外部サービス障害時にコネクションプールを圧迫する。メールの送信はロールバックできない。一般にも「トランザクション内で外部 I/O を行わない」という原則から逸脱する。

**不採用理由:** 外部 I/O をトランザクション内に入れるデメリットを許容できないため採用しない。

### 案3: メール送信成功後に招待を作成

- メリット: メール送信失敗時に DB への書き込みが一切発生しない
- デメリット: メール送信成功後に DB 書き込みが失敗すると、メールだけ飛んで招待レコードが存在しない状態になる。ユーザーが accept URL をクリックしても招待が見つからない

**不採用理由:** 「メールは届いたが招待が存在しない」状態はユーザー体験として最も悪い。孤立した招待が残る方が管理者による手動削除で回復可能であり、影響が小さい。
